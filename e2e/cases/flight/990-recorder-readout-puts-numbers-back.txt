# The Recorder readout (#990): a point on the graph becomes a number.
#
# The window normalises every visible channel onto its OWN min..max, so a line's
# height carries shape and timing but no value, and no label can carry one either
# -- implot hashes the whole plot-item label, which is what made the first version
# of this window churn colours and grow its item pool every frame (kRecChans spells
# that trap). So the value belongs to a SAMPLE instead: click the graph and the
# window prints that sample's readings, through the one formatter that also draws
# the rows -- which is what makes a dash a dash here exactly as it is a dash in the
# file.
#
# Three claims, all of them about the number rather than the pixels:
#
#   1. The click lands on the sample the pointer is over, on the MISSION clock:
#      t=23.00 s sits inside the ring's 19 s span, the same x axis the plot pins to.
#      Not the file's t= column (recorder.h shouts about that in capitals), so a
#      warp coast keeps the pointer proportional.
#
#   2. The numbers are the ring's own, and therefore the trace's: ONE sampler feeds
#      both sinks (#966/#972's rule), so alt_asl=268.469 v=0.0281101 here is the row
#      the flight log wrote at that moment, not a second reading taken for the
#      picture. They print as %.6g, enough digits to tell 45210 from 45211.
#
#   3. A channel toggled on appears in the pinned line, and a second click on the
#      same sample lets go. The toggle is the same hud.rec_chan state the checkboxes
#      set, so the printed line and the picture agree about what is drawn -- the
#      readout lists the visible subset, in table order.
#
# The click is scripted with --sim-mouse pixels rather than --ui-click because the
# plot is not a widget, so there is no label to name. The pixel comes from the
# at=/size= the window prints at appearing time (at=496,372 size=560,340), which is
# also what pins its anchor; 776,620 is inside the plot frame the window measures
# for its own wheel/drag test. The Pause at 8000 ms is what makes the click
# deterministic: a live ring keeps growing, so the x range -- and so the sample that
# pixel means -- moves under the cursor between frames.
#
# Why not assert the hover readout instead of the pinned one: hover draws the same
# rows but prints nothing, so it is the eye's business. Pinning is the half that
# leaves evidence, and it is the half a player uses to move the pointer away.
NAME recorder-readout-puts-numbers-back
CLAIM Clicking the Recorder graph pins a readout of that sample's readings on the mission clock, a toggled-on channel appears in it, and clicking the same sample again releases it.
KIND invariant
ARGS --time-accel 4 --width 1280 --height 720 --startship stager,res/ships/stager.json,Kerbin,pad
ARGS --sim-steps 900 --record --record-interval 0.25
ARGS --sim-press 4000,100,SPACE
ARGS --ui-click 2000,"Windows/Recorder"
ARGS --ui-click 3000,"Recorder/Start"
ARGS --ui-click 7000,"Recorder/gamma"
ARGS --ui-click 8000,"Recorder/Pause"
ARGS --sim-mouse 8400,0,776,620,1
ARGS --sim-mouse 8800,0,776,620,1
EXPECT [recwin] pin t=23.00 alt_asl=268.469 v=0.0281101 q=20.1511 aoa=-89.9779 gamma=0.000653727
EXPECT [recwin] unpin
FORBID FAILED
