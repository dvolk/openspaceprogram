# --power-log prints the whole electrical model in one row -- generation,
# constant draw, stored charge, the active draw (#643), and the powered= gate the
# reaction wheels live behind -- and nothing in the battery could read any of it:
# run.py had no parser for [powerlog] and no case asserted a thing about it
# (#377). So a ship that stopped MAKING power, or stopped LOSING it, kept its
# battery bar green.
#
# power_test is the smallest ship that shows all of it: a 600 W capsule, a
# 298.45 W RTG and a 2250 W wheel on a 12000 Wh battery. The RTG does NOT cover
# life support, so the battery has to fall over a coast. That is the #379
# regression: a substep's 4.65e-4 Wh sat under half a float ULP at 12000, so
# drainEC's `have - share` rounded straight back to `have` and the charge sat at
# exactly 12000.0 Wh while coasting, moving only while the wheels worked.
#
# The invariant that ties a row together is that the charge slope equals the
# watts the SAME row prints. The case names the ship's parts once -- to say
# which ship it flew -- and never uses them to predict the charge, so a parts
# rebalance moves the identity pin only, and a battery that lies still fails.
NAME power-log-balances-the-battery
CLAIM --power-log's charge moves at the rate its own printed watts imply.
KIND golden
ARGS --timeout 20 --startship power_test,res/ships/power_test.json,Kerbin,rot-orbit
ARGS --power-log --sim-press 3000,5000,W
EXPECT [powerlog]
FORBID error:
FORBID FAILED
# The ship's own numbers, steady on every row: one RTG, one capsule, one 12 kWh
# battery, and the wheels stay online the whole time because there is charge.
CHECK len(power) >= 20
CHECK all(r["gen"] == 298.4 and r["const_draw"] == 600.0 and r["capacity"] == 12000.0 for r in power)
CHECK all(r["powered"] == 1 for r in power)
CHECK all(0.0 <= r["charge"] <= r["capacity"] for r in power)
# Generation is under the constant draw, so the pool can only ever fall. A
# rising charge would mean the balance was computed somewhere other than where
# the watts are printed.
CHECK all(b["charge"] <= a["charge"] for a, b in zip(power, power[1:]))
# Coasting before W is pressed, and coasting again after it is released: the
# charge has to actually move. On the float store both spans read flat --
# 12000.0 throughout the first, 11996.5 throughout the second -- so these two
# are the assertions #379 fails.
CHECK first([r for r in power if r["t"] < 3.0])["charge"] > last([r for r in power if r["t"] < 3.0])["charge"]
CHECK first([r for r in power if r["t"] > 8.5])["charge"] > last([r for r in power if r["t"] > 8.5])["charge"]
# The post-release coast is the long one (rows 8.6 -> 19.8 s), which is what makes
# the slope readable at all: charge prints to only 0.1 Wh, so the 0.9 Wh that moves
# across the window carries ~10% quantisation (a 0.5 s row at 302 W net is 0.042 Wh,
# so several rows print the same value in a row) -- comfortably inside the 20% band,
# where two adjacent rows would be all rounding error. The expected Wh/s comes out of
# the gen= and const_draw= the rows themselves print, not out of parts.json.
CHECK abs((first([r for r in power if r["t"] > 8.5])["charge"] - last([r for r in power if r["t"] > 8.5])["charge"]) / (last([r for r in power if r["t"] > 8.5])["t"] - first([r for r in power if r["t"] > 8.5])["t"]) - (power[0]["const_draw"] - power[0]["gen"]) / 3600.0) < 0.2 * (power[0]["const_draw"] - power[0]["gen"]) / 3600.0
# Commanding attitude adds the wheel's draw, and the rows print that term now
# (#643), so this window gets the SAME identity as the coast above instead of the
# ratio this case used to have to settle for around the missing column. The
# expected Wh/s is the mean of the watts those same rows print, active included;
# the observed is the charge they print: 11999.1 -> 11996.3 over the rows spanning
# 3.9 -> 7.5 s, 2.8 Wh where those rows' 2776.6 W implies 2.78 Wh -- under 1%. The
# band is 10% rather than tighter because the RHS is a mean of INSTANTANEOUS rows,
# which only matches while `active` is constant across the window (the CHECKs below
# pin that) and because the log's 0.1 Wh print costs ~4% at this scale.
CHECK abs((first([r for r in power if 3.6 < r["t"] < 7.6])["charge"] - last([r for r in power if 3.6 < r["t"] < 7.6])["charge"]) / (last([r for r in power if 3.6 < r["t"] < 7.6])["t"] - first([r for r in power if 3.6 < r["t"] < 7.6])["t"]) - sum(r["const_draw"] + r["active"] - r["gen"] for r in power if 3.6 < r["t"] < 7.6) / len([r for r in power if 3.6 < r["t"] < 7.6]) / 3600.0) < 0.1 * sum(r["const_draw"] + r["active"] - r["gen"] for r in power if 3.6 < r["t"] < 7.6) / len([r for r in power if 3.6 < r["t"] < 7.6]) / 3600.0
# What the active column means: it is the hull's BILL, not its rating (#599's
# same split). Nobody is commanding before W, so it reads 0; holding W has it
# billing the wheels AND the pod's built-in drums (#596). Each CHECK guards its
# own window's size first: `all(...)` over an empty filter is vacuously true, and
# a row filter can only be assumed non-empty here, never known. (No CHECK carries
# a trailing message either -- run.py evals the whole line, so `expr, "note"` is a
# non-empty tuple and therefore always true.)
CHECK len([r for r in power if r["t"] < 2.8]) >= 3 and all(r["active"] == 0.0 for r in power if r["t"] < 2.8)
CHECK len([r for r in power if 3.6 < r["t"] < 7.6]) >= 5 and all(r["active"] > 0.0 for r in power if 3.6 < r["t"] < 7.6)
CHECK max(r["active"] for r in power) > 2000.0
