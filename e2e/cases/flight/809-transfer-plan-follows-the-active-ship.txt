# A transfer plan belongs to a PAIR -- the subject hull and the target -- but the
# planner's dirty set only ever remembered the target (#809). Switch to another of
# your own vessels around the same body and the plan survived for up to 30 frames:
# the map drew the NEW hull's position with the OLD hull's departure velocity, the
# burn billboard pointed along that, and the TARGET window printed a dv belonging
# to the hull you left. Nothing asserted and the 30-frame refresh made it self-heal,
# which is why it hid.
#
# It also hid in the LOG: an [xferlog] line named its target and never the hull the
# plan was solved from, so a row carrying someone else's journey was unreadable as
# one. The line gained ship="<hull>" for exactly that, and this case is what the
# field buys -- one assertion per hull, no time bands and no cross-log correlation:
# a plan printed under a hull's name must be THAT hull's journey.
#
# racer sits on the pad and transporter already holds orbit, so the same Mun target
# is not remotely the same trip -- a launch out of a gravity well (~3.5 km/s) versus
# an escape from an orbit already held (~1 km/s). Margins are wide because the
# numbers ride the phasing search and the body files; the gap between the journeys
# does not. The --orbit-interval only matters for CATCHING a leak: the stale window
# is 30 frames (~0.5 s), so sampling at 0.2 s puts one or two rows inside it. The
# rule itself is pinned exactly, without a frame or a millisecond of luck, in
# tests/test_hooks.cpp::test_solve_is_stale.
#
# Teeth, measured: with BOTH defenses deleted (the subject term out of the dirty set
# and the solve no longer dropped when the active hull changes -- i.e. the state
# before this fix), the run dies on the planner's own assert that a logged plan
# belongs to the hull in control, three samples after the click. With either defense
# left in, the case still passes: they are a belt and its braces, and the assert is
# what says so.
NAME transfer-plan-follows-the-active-ship
CLAIM With a transfer target held, every plan the game prints belongs to the hull in control -- including the frames right after switching to another of your own vessels.
KIND invariant
ARGS --startships e2e/fixtures/startships.json --timeout 12
ARGS --xfer-log --orbit-interval 0.2 --transfer-target Mun
ARGS --ui-click 2500,"Windows/Ship List"
ARGS --ui-click 3000,"Ship List/transporter"
EXPECT Active ship 5 of 8: transporter
FORBID error:
FORBID not plannable
CHECK len(xfer) >= 6
CHECK all(r["target"] == "Mun" for r in xfer)
# Both hulls really got planned, so the pairing below is not vacuous.
CHECK any(r["ship"] == "racer" for r in xfer)
CHECK any(r["ship"] == "transporter" for r in xfer)
# THE regression: each row's numbers must be its own subject's. With the subject
# out of the dirty set, the rows right after the click carry transporter's name and
# racer's launch -- a pad hull's departure velocity billed to a hull already in orbit.
CHECK all(r["total"] > 3000 for r in xfer if r["ship"] == "racer")
CHECK all(r["total"] < 1500 for r in xfer if r["ship"] == "transporter")
# And the switch is the only thing that moves: nobody's plan appears before it.
CHECK min(r["t"] for r in xfer if r["ship"] == "transporter") > max(r["t"] for r in xfer if r["ship"] == "racer")
LIMIT 60
