NAME platform-drifts
CLAIM The balloon platform drifts east at the authored wind speed, a pure function of the clock.
KIND invariant
ARGS --system res/systems/solar_system.json --time-accel 10
ARGS --startship skiff,res/ships/skiff_gear.json,Venus,pad,site=venus_cloud_platform
ARGS --timeout 20 --dbg-log --orbit-log --orbit-interval 2.0
EXPECT [bldg]
EXPECT [dbg]
EXPECT [orbitlog]
# 200 s of sim at 10x warp: the platform advances east ~86.29 m/s along its
# latitude circle. A pose that only advanced with the physics tick -- or accumulated
# phase -- would miss this.
#
# The speed is measured PER STEP, not between the two ends (#857). The first version
# multiplied 86.29 by (last t - first t), and both of those timestamps are printed to
# 0.1 s: at 86.29 m/s a tenth of a second is 8.6 m, so the 5 m window was smaller than
# the measurement's own noise -- 15604.5 m of chord against 15609.9 m of arithmetic,
# red by 0.34 m with nothing wrong in the engine (the step gaps it summed printed as
# 20.2, 20.0, 20.2, 20.0, 20.1, 20.2, 20.2, 20.0, 20.0). One step is 20 s
# (--orbit-interval 2.0 at 10x warp) over ~1730 m of travel, so its dt can still be
# off by a tenth at each end: 1730/20.0 against 1730/20.1 is 0.43 m/s, which is why
# the window is 0.75 and not 0.05. Measured across the nine steps: 86.15 to 86.65 m/s.
# The arc's chord sag is 6e-6 m per step, so at this scale the geometry really is exact.
CHECK (lambda pl: all(abs(sum((b["pos"][i]-a["pos"][i])**2 for i in (0,1,2))**0.5/(b["t"]-a["t"]) - 86.29) < 0.75 for a, b in zip(pl, pl[1:])))([b for b in bldg if b["id"]=="venus_cloud_platform"])
# The steps to walk. Without this the CHECK above is `all()` over an empty zip if the
# id ever changes -- the runner's row guard proves [bldg] lines were parsed, not that
# any of them is THIS platform.
CHECK len([b for b in bldg if b["id"]=="venus_cloud_platform"]) >= 9
# East is -Z at lon 0 (equirect.h): the platform moves that way, and holds radius.
CHECK [b for b in bldg if b["id"]=="venus_cloud_platform"][-1]["pos"][2] < [b for b in bldg if b["id"]=="venus_cloud_platform"][0]["pos"][2] - 1000
CHECK all(abs(b["r"] - 6107800) < 1 for b in bldg if b["id"]=="venus_cloud_platform")
# The ship rides along at warp too: in the platform's bubble (#850) it is at
# rest on the deck -- bubble-local pos bounded, frame-local speed ~0 -- while
# the building itself drifts 1.7 km per log step above.
CHECK "bubble" in orbit[-1]["frame"]
CHECK sum(p*p for p in dbg[-1]["pos"]) < 10000
# |v| here is the frame-local speed at the sampling instant, which for a hull on landing gear is
# contact-solver jitter rather than motion, and it is not stable between runs: the last three
# rows read 0.40 / 0.13 / 0.28 before #945 and 0.40 / 0.17 / 1.01 after it (a re-run of the same
# build lands 0.52). The row that went red printed vel = [-0.98 -0.04 -0.26] |v| = 1.01 beside a
# pos of [-38.9 -0.0 1.6] -- the SAME point as the row before it, so nothing moved in those 20 s.
# #945 leaves the parts behind others out of the hull's cd vote (the billed area is unchanged), so
# the wind's force on a parked hull and the point it acts at both move, and the gear jitter with
# them; the band goes 1.0 -> 1.5 to cover a spread this case cannot control. The claim the band
# was standing in for is REST, so it is pinned below directly, as displacement across the last two
# log steps: measured 0.3 m over 40 s, against the platform's own 3450 m in the same span. What
# the ship does before that (before #945 too) is creep -4.8 m per step from x=-5.0 to x=-38.9 and
# stop.
CHECK abs(dbg[-1]["v"]) < 1.5
CHECK (lambda d: sum((d[-1]["pos"][i]-d[-3]["pos"][i])**2 for i in (0,1,2))**0.5 < 8.0)(dbg)
CHECK all(abs(o["r"] - 6107800) < 100 for o in orbit)
