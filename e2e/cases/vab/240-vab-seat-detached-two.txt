# Two capsules, both named, and the SECOND one is detached out of the build (a
# lone part is deleted rather than stashed). The plan for the part that left is
# dropped; the plan for the one that stayed must still fly. The ids here are
# longer than std::string's small-buffer on purpose: reading the erased entry
# after vector::erase then showed up as mojibake in the toast instead of a
# plausible part name, and a shorter id hides it.
#
# Everything here is the player's route now. --ui-focus names a capsule, the game
# finds a pixel that picks it, and the RMB there opens that capsule's part window
# -- click the seat, click the person. The detach is the same shape: aim, click,
# then "Detach subtree". The "[vab] select" line says which part the click took;
# --vab-detach 1 used to select by index and never checked that a pick landed on
# part 1.
#
# The detach aim still happens AFTER both part windows have been opened, and that
# is the ordering to watch: a click inside a part window is swallowed by the
# window (correct behaviour), and the aim's spiral only asks the 3D pick whether a
# pixel hits the part -- it does not know about windows. Only ONE part window is
# on screen at a time (VabState::partWinId, game.h:245; opening another capsule's
# window replaces it, vab.cpp:906), so at the detach aim the live window is
# capsule_r1.5h3_1's: measured at 1080p it starts 12px right of the click that
# opened it and its seat rows span 980,607-1288,675, while the aim for
# capsule_r1.5h3_2 reports 960,643 -- 12px clear of its left edge. That margin is
# thin and it is luck: the window is placed against the OTHER capsule's pixel, and
# the dossier's stat block pushes the seat rows down into the row band this aim
# sits in. If this case ever stops selecting, check whether the window now covers
# the reported pixel.
NAME vab-seat-detached-two
CLAIM Detaching one of two named capsules keeps the other's plan.
KIND invariant
ARGS --kerbals e2e/fixtures/three_kerbals.json
ARGS --width 1920 --height 1080 --time-accel 1 --timeout 19 --frame-cap 30
ARGS --ui-focus 9000,capsule_r1.5h3_2
ARGS --sim-mouse 9100,0,CUR,CUR,RMB
ARGS --ui-click 9600,"Capsule (3m)##capsule_r1.5h3_2/Seat 1##s0"
ARGS --ui-click 10000,"##Combo_00/Ace"
ARGS --ui-focus 10400,capsule_r1.5h3_1
ARGS --sim-mouse 10500,0,CUR,CUR,RMB
ARGS --ui-click 11000,"Capsule (3m)##capsule_r1.5h3_1/Seat 1##s0"
ARGS --ui-click 11400,"##Combo_00/Bram"
ARGS --ui-focus 12000,capsule_r1.5h3_2
ARGS --sim-mouse 12500,0,CUR,CUR,LMB
ARGS --ui-click 13000,"VAB/Detach subtree"
ARGS --ui-click 15000,"VAB TopBar/LAUNCH"
# Reached the way a player reaches the editor: Title Menu -> New Game -> Start, then
# the 4 key.
# Game Debug turns on dev vehicles, which is what puts this def in the
# Load picker; the filter narrows the roster to one row, and row + Load
# do the rest. Same vabLoad() either way, so the assertions below are
# unchanged -- and every scripted event here is shifted +7000ms because
# the editor opens at 2.6s, not at boot.
ARGS --ui-click 1000,"Title Menu/New Game"
ARGS --ui-click 1600,"New Game/Start"
ARGS --sim-press 2600,0,4
ARGS --sim-press 3100,0,F1
ARGS --ui-click 3600,"Game Debug/Dev vehicles in the VAB picker"
ARGS --sim-press 4100,0,F1
ARGS --ui-type 4600,"VAB TopBar/##vehfilter",two_capsules
ARGS --ui-click 5100,"VAB TopBar/##vabload"
ARGS --ui-click 5700,"two_capsules"
ARGS --ui-click 6300,"VAB TopBar/Load"
