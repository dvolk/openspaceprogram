NAME approach-ladder-points-out-of-the-targeted-port
CLAIM A targeted docking port shows a ladder of 2 m squares normal out of the face it presents to the armed hull, sized and spaced by one set of constants, and it stops when the dock consumes the intent.
KIND invariant
# --dock-test approach arms dockprobe's port at dockstation's and closes at 0.09 m/s, so the
# intent -- the thing #1146 draws on -- is live from the first painted frame and dies at the
# mate about 2.2 s in. The ladder is ten GL_LINE_LOOP draws in the world pass with depth on:
# no stdout row can prove a rasterizer lit them, so every CHECK below is against the placement
# the painter was handed, and none of them claims pixels.
#   rungs/edge/step  what is drawn, from the constants in vehicle.h. The ticket's numbers
#                    (2 m squares, every 2 m, 20 m of ladder) are tuning, not physics. They are
#                    printed FROM those constants, so pinning them here catches a format change
#                    and a rename, not a wrong value. The reach and where it stops counting are
#                    pinned with teeth in tests/test_dock.cpp (dockRungAt's edges against the
#                    gate's own faceGap), and 1146-b pins the crossing on a fixture that really
#                    gets 20 m away.
#   why              the capture gate's verdict -- the same token [dockwin] prints, because one
#                    table in vehicle.cpp says both and they cannot drift. It is here because
#                    the ladder ASKS the gate before drawing. The geometric refusals DO draw:
#                    these rows read why=toowide, which is the truth at 0.22 m and 0.13 m of
#                    face gap for a pair that captures inside 0.10 m, and flying along the bore
#                    is how a pilot fixes a wide approach. The pair-level refusals (target on
#                    the rails, a hull in another frame, no armed port) draw nothing; which of
#                    the 13 verdicts is on which side is pinned in tests/test_dock.cpp, because
#                    no --dock-test fixture can put a TARGET on the rails, so no e2e row can
#                    reach that branch.
#   axis             the port's bore, unit length. A ladder that ignored the port's own frame
#                    -- screen-oriented instead of port-oriented -- still prints a unit vector
#                    here, so this column alone does not pin "oriented with the port"; the
#                    ru/rv pins in tests/test_dock.cpp do (measured: a camera-basis rung still
#                    passes every row here). What it DOES pin is that the mouth the rungs run
#                    out of is the bore the capture gate measures along.
#   faceout/near     the gap between the two PRESENTED faces measured along the target's bore --
#                    face to face, not port centre to port centre and not to the hull's COM --
#                    and which rung that highlights. This pair starts short and closes, so
#                    faceout sits inside the first rung the whole run and near is 1. The step
#                    between rows is the closing rate: measured 0.222 -> 0.132 m over 1 s, the
#                    fixture's 0.09 m/s. Past the ladder's 20 m reach near reads 0 rather than
#                    sticking at the last rung, which 1146-b pins at 21.0 m.
#   drawn=0 why=     the intent is consumed by the mate (Game::updateDocking clears both halves),
#                    so the ladder stops, and the row says why in the gate's word: noarm, a hull
#                    with nothing armed. A row for the negative branch matters for the same
#                    reason #873's does: a feature that silently stopped drawing is otherwise
#                    indistinguishable from one that never ran.
# WHAT THIS CASE CANNOT CATCH, measured rather than assumed: deleting the ten Draw calls,
# turning the rungs screen-oriented and moving them to the wrong spacing all leave every row
# here byte-identical, because the row reports the placement the painter computed, not what GL
# lit. Removing the drawDockLadder CALL reddens all four CHECKs. The ten draws themselves are
# visible one level up, in [perf]'s draws= column (+10 measured per frame with the intent
# live), which is where #1168 suggests pinning them.
ARGS --dock-test approach --time-accel 1 --timeout 8 --dockhud-log --orbit-interval 1.0
EXPECT Dock-test (approach)
EXPECT [dock] t=
EXPECT [dockhud] t=
# The rung constants and the gate verdict the painter was working under, on every row it drew.
CHECK (lambda r: len(r) >= 2 and all(a[0] == "toowide" and a[1] == "10" and a[2] == "2.00" and a[3] == "2.00" for a in r))(re.findall(r'\[dockhud\] t=\S+ target="dockstation" port=docking_port_r1 why=(\w+) rungs=(\d+) edge=([-\d.]+) m step=([-\d.]+) m ', out))
# The bore the rungs run out of is unit length, the face gap sits inside the first rung, and
# that rung is the highlighted one.
CHECK (lambda r: len(r) >= 2 and all(abs(sum(float(v) * float(v) for v in a[0].split()) - 1.0) < 1e-3 and 0.05 < float(a[1]) < 1.0 and a[2] == "1" for a in r))(re.findall(r'axis=\[([-\d. ]+)\] faceout=([-\d.]+) m near=(\d+) drawn=1', out))
# Two rows 1 s apart, closing at the fixture's 0.09 m/s. The band is the print step of the
# gate rather than the physics: those rows measured 0.222 -> 0.132, so 0.090. (One capture
# group, so findall hands back strings, not 1-tuples -- r[0] is a whole number here.)
CHECK (lambda r: len(r) >= 2 and abs((float(r[0]) - float(r[1])) - 0.09) < 0.03)(re.findall(r'\[dockhud\] t=\S+ target="dockstation" port=docking_port_r1 why=\w+ rungs=\d+ edge=[-\d.]+ m step=[-\d.]+ m face=\[[-\d. ]+\] m axis=\[[-\d. ]+\] faceout=([-\d.]+) m near=\d+ drawn=1', out))
# And it stops once the dock has consumed the intent -- in the gate's own token, never a word
# this row coined.
CHECK (lambda r: len(r) >= 1 and all(a == "noarm" for a in r))(re.findall(r'\[dockhud\] t=\S+ drawn=0 why=(\w+)', out))
