NAME the-shipped-corpus-flies-comets-and-calls-them-comets
CLAIM The default corpus authors seven comets, the dossier calls each one a comet rather than an asteroid or a planet, each is named by its MPC designation, and the designation rule is what keeps 252P/LINEAR from being a second body called LINEAR.
KIND invariant
ARGS --system res/systems/solar_system.json --timeout 6 --atlas-dump 4000
# Comets entered the corpus as seven (reports/comets2026_11_12, #786): one per kind of play,
# from utils/rss/asteroids/comets.py over the MPC's allcometels file. They are a BodyType of
# their own (src/terrain.h) for the same reason DwarfPlanet is one -- the render path and the
# laws are the asteroid's, and the DOSSIER has to be able to say what the body is. --atlas-dump
# builds those rows through the same atlasDossier() the Science tab renders (#385), so this
# pins what a player reads without a GUI.
#
# 1. SEVEN, AND EACH ONE SAYS SO. A count rather than seven EXPECTs: the number is the roster,
#    and a comet that loads but types as "planet" (the ternary-chain default this replaced) is
#    the failure mode -- the count moves and every type row beside it disagrees.
EXPECT [atlas] 1P/Halley weight=
EXPECT [atlas] 252P/LINEAR weight=
CHECK out.count("[atlas]   type                   comet") == 7
CHECK out.count("[atlas]   type                   planet") == 9
# 2. THE HANDLE IS THE DESIGNATION, NOT THE NICKNAME. The deeper corpora already ship a body
#    called LINEAR -- asteroid 118401, a MAIN-belt comet at a 3.20 AU and e 0.19 -- while
#    252P/LINEAR is a Jupiter-family comet at a 3.05 AU and e 0.67. Names are keys here (the
#    catalogue, saves, --startship, --transfer-target), so one name on two worlds is a second
#    planet with an indistinguishable handle, and the asteroid collision pass has no number to
#    disambiguate a comet with. The bare name stays out of the file that a new game boots.
FORBID [atlas] LINEAR weight=
# 3. AND THE FAR RAILS LOAD. C/1811 F1 sits 253.8 AU from the Sun at the catalogue epoch --
#    further from the star at that epoch than any other body in this file (Eris is next at
#    97 AU) -- and reaches 409.8 AU at apoapsis, inside the star's 6,684 AU universe bound.
#    Deeper RAILS exist in the same file (Sedna's apoapsis is 1,011 AU, 2015 RM306's 527 AU);
#    what comets add is bodies that are out there NOW, not just on rails that reach there.
#    The dossier printing an apoapsis in AU at all is the check: fmt_dist switches unit past
#    1 Tm, and a rail that overflowed or arrived as an ellipse-clamped stand-in prints a
#    different row rather than failing loudly.
CHECK (lambda blk: re.search(r"semi-major axis\s+[\d.]+ AU", blk) and float(re.search(r"apoapsis\s+([\d.]+) AU", blk).group(1)) > 400.0)(re.search(r"\[atlas\] C/1811 F1 \(Great comet\) weight=.*?(?=\n\[atlas\] [^\n]* weight=|\Z)", out, re.S).group(0))
# 4. THE SOI ON A 300 m NUCLEUS IS A FLOOR, NOT A DERIVATION, and #785 says that floor is
#    wrong. So pin the MAGNITUDE, not the ordering: an SoI above the near-body shell is
#    guaranteed by the loader (inertialSoi takes a max, and validateBodyLimits throws if the
#    ordering ever inverts), so "shell < SoI" could not fail for any body that boots. The
#    ratio can fail, and it should when #785 is fixed: 252P's sphere is currently 451 times
#    its own radius (135.3 km around 300 m), which is the number that ticket exists to shrink.
#    (Both block patterns above end at the next line that STARTS a dossier, not at
#    "\[atlas\] \w+ weight=": a designation like "C/1965 S1 (Ikeya-Seki)" has spaces, so the
#    \w+ form silently spans three bodies and would read the wrong one's apoapsis.)
CHECK (lambda blk: (lambda r_km, soi_km: soi_km / r_km > 100.0)(float(re.search(r"radius\s+([\d.]+) m", blk).group(1)) / 1000.0, float(re.search(r"SoI\s+([\d.]+) km", blk).group(1))))(re.search(r"\[atlas\] 252P/LINEAR weight=.*?(?=\n\[atlas\] [^\n]* weight=|\Z)", out, re.S).group(0))
