### 2.1 — containment edge, unused  (done, committed cf28065)

Decisions (report left them open):

- Ownership: `contents` is NON-OWNING through phases 2-4, and the owner for
  inventory items is DEFERRED TO PHASE 5 (report step 2.1's second option).
  Rationale: an owning ~Part would double-free an aboard kerbal
  deterministically — ~Vehicle deletes crew (vehicle.cpp:1274-1276) BEFORE
  its parts (:1279). Documented in part.h where the fields live.
- The XOR invariant has a phase-2 exception: an aboard kerbal's part is BOTH
  attached (owner = its Kerbal vehicle shell) and contained (container = the
  capsule). The report's "never both" is the phase-5 end state. So the check
  is: every part's owner back-reference holds; a contained part's owner MUST
  be a character (isEva()); a capsule may only hold character parts; the
  container/contents back-references agree. Enforced via
  Vehicle::checkPartInvariants(), asserted from rebuildCompound (every
  build/stage/refresh) next to checkCompoundInvariants.
- checkPartInvariants RETURNS a bool (with a [part] diagnostic) instead of
  asserting itself: rebuildCompound asserts it (same hard-fail style as
  checkCompoundInvariants), and the headless test can call it directly and
  check the negative cases. assert() is uncatchable, which would make the
  "check actually fires" test impossible.
- `owner` is wired in the two attach primitives (setRoot/attach — covers
  build, load, docktest/radialtest and the hand-built test ships), then
  re-pointed in absorbShip (B's parts → survivor) and extractSubtreeAsShip
  (dropped side → new ship). A Part* is stable across both, so only the
  owner pointer moves.
- Test (tests/test_contain.cpp) uses a local `struct TestCrew : Vehicle`
  overriding isEva(), NOT the real Kerbal: eva.cpp includes game.h, which
  drags the whole game into a headless test link. The invariant is keyed on
  the isEva() virtual, so the stand-in exercises the same code path.

BUG found while running 2.2 (was latent in the 2.1 commit): the owner
wiring only happened in setRoot/attach, but the pre-existing hand-built-ship
tests (test_fuel, test_inertia, ...) add parts via `parts.push_back` and never
go through the attach primitives, so their parts had `owner == nullptr` and
`rebuildCompound`'s `assert(checkPartInvariants())` aborted the whole `make
test` at test_fuel. (So 2.1 was committed with a red `make test` — the
"green" claim in the phase-1 verification above was for the OTHER suites;
test_fuel onward never ran.) Fix: `rebuildCompound()` now wires
`p->owner = this` for every part (the parts list is the ownership list) right
before the assert — one place, covers init→finalize, direct calls (test_
inertia), and the merge/split paths. The attach primitives' owner-setting is
redundant now but harmless (idempotent). `make test` is fully green again.

### 2.3 — save the containment edge by uid  (done)

What changed:
- save.h: `SaveShip::aboard_part` is now `uint64_t` (the capsule's uid), not
  an `int` index into the aboard ship's part list. The reader uses the strict
  `readUid` helper (a string/float/negative reads as the "absent" 0 sentinel,
  same handling as controller / dock ports / fuel links) instead of a bare
  `.get<int>()`. The struct comment documents why: a uid is stable across a
  merge/split and order-independent, and 0 = absent/free.
- save.cpp writer: `s.aboard_part = k->aboardPart->uid` (was a loop mapping
  the Part* back to an index). 0 for a free (EVA) kerbal.
- save.cpp reader (buildKerbalFromSave): now takes the load's
  `savedUidToPart` map (populated before the crew, which always follows its
  ship) and validates THREE things, throwing a clean load error for each:
  (1) aboard_part 0 = a save predating uid-keyed crew -> refused (not parked in
  part 0); (2) the uid must name one of THIS ship's parts (findSavedPart
  membership) -> a reordered/foreign save is refused; (3) the part must be a
  capsule (def->crew_capacity > 0) -> the check report 1.4 notes did not exist
  (a reordered save could park a kerbal in a fuel tank). findSavedPart moved
  into the anonymous namespace (it was after save_game, too late for the crew
  builder); both load paths now resolve through it.

Format migration (the breaking change the report expects, per QWEN.md no
back-compat): the two committed crew fixtures were in the old index format
(aboard_part 0 = the capsule). Migrated both to the capsule's uid (1):
e2e/fixtures/save_racer/ships/v1.json and e2e/fixtures/save_corrupt/ships/v1.json.
save_docked has no crew. This is why 54-save-load and 65-reload-refused still
pass -- the 65 case's failure still lands on v2 (the bad part), not v1 (the
kerbal now builds fine).

New e2e 81-crew-noncapsule: e2e/fixtures/save_racer_badcrew (a copy of

## Phase 3 work log (derived mass)

Plan (design report §4): 3.1 Part::effectiveMass (unwired) → 3.2 wire

### 3.1 — Part::effectiveMass, unwired  (done, committed 11bbaee)

Added `Part::effectiveMass()`: its own body mass plus the effectiveMass of
every contained part, recursively. The header documents it as a pure
derived value, non-owning (the traversal only reads), acyclic by
checkPartInvariants (each contained part has at most one container).

New tests (tests/test_contain.cpp, +12 checks): effectiveMass on a part
with no contents = body->mass; on a part with two contained parts = body +
both; on a nested containment = the full sum. 48 checks total, all pass.

### 3.2 — wire effectiveMass into the compound  (done, committed e6f8ad7)

What changed:
- vehicle.cpp rebuildCompound: `masses[i] = p->effectiveMass()` (was
  `p->body->mass`). The compound now carries the crew's mass without baking
  it into the body.
- vehicle.cpp compoundCom: `m = parts[i]->effectiveMass()` (was `body->mass`)
  — so the COM includes the crew.
- vehicle.cpp checkCompoundInvariants: `m = parts[i]->effectiveMass()` +
  the inertia tensor is scaled from the body mass up to the effective mass
  (inertia is linear in mass for a fixed shape) + the parallel-axis term
  uses the effective mass. This matches what Bullet does in
  calculatePrincipalAxisTransform (it scales the shape's inertia to the
  reported mass).
- vehicle.cpp applyGravity + fictitious + getMass: `p->effectiveMass()` (was
  `p->body->mass`). CRITICAL: the force must carry the same mass as the COM
  and the inertia (both derived from effectiveMass), or the net force misses
  the crew and acts off the true COM, adding a spurious dcom x F torque.
  This was the root cause of the com-torque e2e regression (48) that appeared
  when 3.2 was first applied — the force paths were still on body->mass.
- vehicle.h: `addPartMass` declaration DELETED.
- game.cpp: the EVA/board paths now call `ship->rebuildCompound()` after the
  containment edge mutates (the crew's mass changes the compound). The
  select_ship/remove_ship guards (isCrewAboard) are KEPT with an updated
  comment (they're about ownership, not mass).
- ships.cpp / ships.h / eva.h: spawn_crew_kerbal sets the containment edge +
  calls rebuildCompound; comment updates.
- save.h / save.cpp: SavePart.mass contract documented as "own body mass"
  (not effective); buildKerbalFromSave calls rebuildCompound after the edge.
- tests/test_inertia.cpp: new `test_contained_kerbal()` case — a TestCrew
  (isEva override) with one part contained in a capsule. Asserts the
  compound mass = capsule + kerbal, the COM = the capsule's center, and the
  inertia tensor = the capsule's inertia scaled to the effective mass + the
  parallel-axis term. Teardown: `delete crew` only (the ship's ~Vehicle
  deletes crew BEFORE parts, so the kerbal's part is freed by the crew's
  ~Vehicle, not by a double `delete k`). 972 checks, all pass.

BUG found + fixed (the com-torque regression): the first 3.2 commit (with
rebuildCompound/compoundCom/checkCompoundInvariants on effectiveMass, but
applyGravity/getMass still on body->mass) made e2e 48 FAIL with a |w| ramp
(~1.3e-3/s) even though tq_log showed |dcom|=0 and |dxF|=0. Root cause: the
force (body->mass, no crew) acts at a lever arm from the COM (which includes
the crew), so there's a constant spurious torque dcom x F. Fix: the force
paths (applyGravity, fictitious, getMass) must use effectiveMass too — the
net force must carry the same mass as the COM and the inertia. After the
fix, e2e 48 passes (|w| flat < 1e-3) and the full suite (29/35/48/54/81/82)
is green.

### 3.3 — point-mass at local pose (DEFERRED, optional polish)

The report's step 3.3 ("a contained part's mass is a point mass at its local
pose, with the parallel-axis term") is the refinement that moves the crew's
mass from the capsule's hull shape to the kerbal's own position. This is
deferred: it is a NO-OP for the current game (kerbals sit at the capsule's
COM, so the point-mass and the smeared-hull give the same COM and inertia).
It becomes a live concern only when phase 4 introduces off-center cargo (a
crate in a bay, a kerbal in a suit that's not at the COM). The current
smearing is correct for the center-of-mass and the inertia tensor; 3.3
would refine the inertia tensor's distribution, which matters only when the
contained part is off-center.

## Quality pass over phase 4 (2026-09-21)

A subagent did a full review of the six phase-4 commits: ownership /
double-free, the pocket-draw path, the containment invariant, save/load
symmetry, the cycle / double-add guards, performance, QoL. Findings
(verified against the code, then fixed -- the fixes are the uncommitted
delta at the bottom of this log, one commit per step was NOT done for the
pass; it lands as a single "quality pass" commit):

BUGs (each reproduced against the tree, then fixed):
- pickUpItem double-free (game.cpp): after inventoryAdd the item is owned
  by dest (in its ownedContents) but was STILL in itemShip->parts, so
  `delete itemShip` (~Vehicle) freed it AND ~Part(dest) freed it again.
  Fix: `itemShip->parts.clear()` before the delete.
- nested-item owner went stale (inventory.cpp/h, game.cpp): moving an item
  that is itself a container (a crate holding a crate) re-pointed only the
  top item's owner; its own inventory subtree kept pointing at the old
  vehicle, so effectiveMass() and teardown used the wrong owner. Fix: a
  recursive inventorySetOwner (item + every nested item), called from
  addToContainer / removeFromContainer / dropItem.
- the pocket draw was dead weight (eva.cpp): phase 4.5 routed the suit's
  RCS through parts[0]->contents, but consumeResourceMass only reaches
  parts in Vehicle::parts (buildFuelGroups groups those), so a pocket tank
  could never be drained -- an empty-suit kerbal with a full pocket still
  could not thrust. Fix: the pocket branch now does the same per-tank
  decrement consumeResourceMass makes (contents resource + body mass;
  refreshCompound picks the mass up).
- partCrew mis-cast inventory items (game.cpp): contents now holds BOTH
  crew and inventory items, and the old body did a blind
  static_cast<Kerbal *>(p->owner) over every entry. Fix: skip any
  p->ownedBy(capPart) (the new Part::ownedBy, part.h -- membership in the
  container's ownedContents is exactly what separates an item from a crew
  member).
- dropItem from a parked carrier (game.cpp): a carrier on rails (or a
  frozen aboard hull) has a stale pose that may sit inside another ship,
  so the item would spawn in collision with the wrong velocity. Fix:
  `if(carrier->onRails) return nullptr;`.

RISKS (hardening, not live crashes):
- containment cycle (inventory.cpp): adding a container into its OWN
  subtree (a crate into a crate it holds) closed a cycle -- effectiveMass()
  recursed forever and ~Part double-freed. Fix: an inSubtree guard in
  addToContainer (refuses dest == item or anywhere under it).
- double add (inventory.cpp): re-adding an already-contained item listed it
  twice in ownedContents, so ~Part freed it twice. Fix: addToContainer
  refuses item->container != nullptr (inventoryTransfer removes first).
- invariant gap: "owned but not listed" (vehicle.cpp checkPartInvariants):
  an item in ownedContents but missing from contents was silently dropped
  from effectiveMass while ~Part still freed it. Fix: a new loop asserting
  every ownedContents entry is listed in contents AND that its container
  pointer agrees. The contents loop now branches on ownedBy: a crew member
  (not ownedBy) must be isEva; an item (ownedBy) must be in a real
  container. The vehicle.h doc comment was rewritten to state both legal
  kinds.
- save/load depth (save.cpp/h): capture and load both went only one level
  deep, silently dropping a crate's own cargo. Fix: depth-first -- SavePart
  carries a nested inventory list of SaveParts, load rebuilds it
  recursively (buildInventoryItems sets each item's owner to the
  container's owner and recurses).
