# Orbital map — investigation + improvement plan

Investigation of the "Orbital map" window and a phased plan to turn it from a
single-orbit debug plot into a proper system map: focus-centered, correct 3D
geometry, child orbits, and transfer/intercept drawing. Written 2026-08-27.

## What it is today

One ImGui window (bottom-left, 480×480), `ui::Window("Orbital map")` in
`src/main.cpp`. A 2D schematic of the **ship's orbit around its current
parent body only**:

- a 26-point ellipse from `o.semi_major` / `o.ecc` (eccentric-anomaly
  parameterization),
- the parent body as a filled circle (`ship->m_parent->radius / div`),
- the ship as a dot + a line to the parent,
- one global `Scale` slider (`static float div`, 5000–100000 m/px),
- true-anomaly / eccentric-anomaly text.
- Hyperbolic orbits (`o.ecc >= 1`) print "no closed orbit to map."

The orbit is drawn in **canonical form** — periapsis always at 3 o'clock:

```
r = a (1 - e cos E);  phi = atan2(sqrt(1-e^2) sin E, cos E - e)
x = r cos phi;  y = r sin phi          // focus at the center
```

That is the correct *shape* (eccentricity) but carries no orientation.

## Problems (why it reads as a debug plot)

1. **Orientation is discarded.** The ellipse is drawn canonical (periapsis at
   +X). `o.raan`, `o.arg_periapsis`, `o.inclination` are all computed
   (`orbit.h`) but never applied. The periapsis/apoapsis markers are literally
   commented `/* incorrect */` (a magic `-M_PI/2`). You see the *shape*
   (eccentricity) but not *where* the orbit points or how tilted it is.
2. **One body, one scale.** It can't show moons around a planet, or the
   planet's orbit around the star. A single shared `div` can't fit a 12,000 km
   moon orbit and a 13,600,000 km planet orbit in the same view.
3. **No transfer view.** A complete Lambert solver + min-dv planner exists
   (`transfer.h`, `planTransfer`), a TRANSFER window shows the numbers, and a
   3D blue burn-direction icon points the departure burn — yet the map never
   draws the transfer conic, the target's orbit, or the intercept point.
4. **Geometry is inlined and messy.** `static float div`, a hardcoded
   `200 + p.x` offset, commented-out dead code, a fixed `pts[26]`. Nothing is
   reusable; extending it means editing the ImGui lambda.
5. **Layout overlap.** The map is drawn at an absolute `(200,200)` offset but
   the cursor is never advanced, so the `Scale` slider + text are laid out at
   the content top-left, over the map.

The math we need **all exists and is already tested**:
`computeOrbitElements`, `propagateKepler`, `planTransfer`, and the frame tree
(`frame->pos/vel`, `->children`, `GetPositionRelTo` / `GetVelocityRelTo`).
This is a *projection + drawing* problem, not a physics problem.

## Target design

A **focus-centered system map** projecting a real reference plane, owned by a
small reusable helper (`src/orbitmap.h`, header-only like `orbit.h`):

- **Focus body** (default = the ship's parent). All geometry lives in the
  focus's inertial frame and is orthographically projected onto the reference
  plane — **XZ, normal +Y**, the plane the bodies orbit in (`railStateFromElements`
  uses `rhat = (cos φ, 0, sin φ)`, so the flat plane is XZ and "up" is +Y).
  The focus sits at the origin (the ellipse focus).
- `project(v3) -> dvec2`: `(cx, cy) + (p.x, p.z) / scale`. This **drops `p.y`**
  (height above the reference plane), which is exactly what makes an inclined
  orbit look squashed. Keeping one shared map plane (rather than the ship's own
  orbital plane) is what lets P2/P3 add other bodies and the transfer conic by
  "projecting more 3D points."
- Draw primitives: `drawOrbit(pts3d)`, `drawBody(radius_m)`, `drawDot(p)`.
- **Scale** = meters/pixel (the existing slider, generalized to zoom).

Because the orbit is generated by *propagating the real state* rather than
re-deriving it from elements, its true 3D orientation shows through the
projection for free — no separate raan/arg-peri/inclination handling needed.

## Phases (each independently shippable)

- **P0 — Refactor.** Extract the projection + drawing into `orbitmap.h`;
  remove the `static div`, the `200 + p.x` magic, the dead comments, and the
  slider/text overlap. Same pixels as today for a coplanar orbit.
- **P1 — Correct geometry.** Sample the orbit by `propagateKepler` over one
  period (exact 3D, so the true orientation shows through the projection).
  Replace the `/* incorrect */` apsis markers with the *actual* periapsis /
  apoapsis points (propagate to `o.time_to_peri` / `o.time_to_apo`). The ship
  dot is `project(orbit_pos)` (was a re-derived `distance·cos φ`). Show the
  inclination readout.
- **P2 — Child orbits.** For each `frame->children` of the focus, draw that
  body's orbit (propagate `child->frame->pos/vel` over its period under
  `parent_mu`) + its dot + a label. Moons around a planet, planets around the
  star, all in the same view/scale.
- **P3 — Intercepts.** For the selected transfer target, draw the **transfer
  conic** (`propagateKepler` of `sol.v_departure` at `r1` over `sol.tof` under
  `mu_parent`), the target's orbit, the departure + arrival points, and an
  intercept marker with `v_inf` / `r_cap`. Reuses the planner's output
  directly — no new math.
- **P4 — Visuals + navigation.** Zoom/pan (the scale slider becomes a real
  zoom), SOI rings, velocity vectors, KSP color coding (ship orbit = green,
  transfer = blue, others = gray), selection highlight, a legend.
- **P5 — Ideas (pick any).** Multi-ship positions + labels; maneuver-node
  preview (ghost orbit after a burn); eclipse/shadow shading of the orbit;
  landing-site marker; hover dv readout; declutter/LOD for the system view.

## Suggested order + verification

**P0 → P1 → P3 → P2 → P4.** P0/P1 fix what is on screen now; P3 is the
highest-value new feature and the cheapest (the solver's output is already
computed each frame); P2 rounds out the system view; P4 polishes. Verify each
phase with `make clean && make && make test && make e2e`, and confirm the map
visually (ask the user to check, per project convention).

## Data sources (for P2/P3)

- **Focus body's children:** `focus->frame->children` (the inertial frames).
- **A child's orbit state:** `child->frame->pos`, `child->frame->vel`
  (relative to the focus, in the focus's inertial frame), and
  `child->frame->parent_mu` for the propagation `mu`.
- **Ship orbit state** (parent inertial frame): `orbit_pos`, `orbit_vel`
  (already computed in the render pass), `mu = ship->m_parent->mu`, and
  `o = computeOrbitElements(...)` for the readouts / `o.period`.
- **Transfer:** `xfer.sol` (`v_departure`, `v_arrival`, `tof`, `r_cap`,
  `v_inf`, `transfer_semi_major`, `transfer_ecc`), `r1` / `v1` (the ship),
  `mu_parent` — see the TRANSFER block in `main.cpp` and `transfer.h`.
