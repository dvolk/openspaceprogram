A. SAME BUG FAMILY AS THE ONE JUST FIXED (stale state across a clock jump)
=====================================================================

A1. [C] Porkchop plan + surface map keep absolute-clock stamps that nothing
    invalidates.                                            COST: S
    WHAT: The transfer planner caches an expensive background computation
      stamped with the sim clock, then turns a chosen plot cell into an
      absolute departure time. Neither is cleared when the clock jumps.
    WHERE: transferplanner.h:97 (pc_computed_at), :104 (xfer_t_dep);
      gameui.cpp:880 (xfer_t_dep = pc_computed_at + pc.t_dep_min);
      gameui.cpp:709 (tleft = xfer_t_dep - time);
      transferplanner.cpp:207 clearPorkchopPlan() -- exists, and is only
      called from transferplanner.cpp:131 and gameui.cpp:725 (Clear button /
      target change), never on a load.
      game.h:554 surfmap_computed_at, set at surfmap.cpp:142, displayed at
      gameui.cpp:1272.
    SYMPTOM: compute a plan at t=5000, pick a departure (~t=9000), then load a
      save at t=78 -> the countdown reads T-8922 s to a departure that is
      meaningless, because the plot was sampled for where the planets were at
      t=5000. Loading a LATER save gives a negative countdown. A system switch
      is worse still (the plan is for the other system's bodies).
    HOW: Game::setTime (game.h, added in 4234fe6) is the hook -- it is now the
      single place the clock moves outside a tick. surfmap_computed_at is a
      Game member, so setTime can reset it in one line. The planner is NOT
      reachable from Game (see D3), so either give Game an epoch counter that
      setTime bumps and have TransferPlanner drop its plan when the counter
      differs, or do D3 first and call clearPorkchopPlan() directly.

A2. [C] Railed ships are integrated step-by-step instead of being analytic in
    time. This is the big one.                    COST: L  (highest value)
    WHAT: Bodies are a pure function of the clock -- UpdateOrbitRails(time)
      re-derives orbit and spin from absolute t every call. Ships on rails are
      not: railsTick advances them by a step.
    WHERE: vehicle.cpp:2907-2912
      propagateKepler(rail_pos, rail_vel, frame->body->mu, step,
                      rail_pos, rail_vel);
      vs frame.cpp:43-71 (bodies, absolute time).
    WHY IT MATTERS: a railed ship's position depends on the HISTORY of
      timesteps, not on the clock. Consequences, all observed in code:
        - a save must store each ship's pose, and a clock jump can never
          re-phase it (this is why a REFUSED load leaves the surviving fleet
          off-epoch -- see the caveat comment now in save.cpp:657-668);
        - warp changes and long high-warp runs accumulate error against the
          analytic bodies;
        - time can never be scrubbed backwards, and "jump to date" is
          impossible without desyncing ships from planets.
    HOW: store conic elements + epoch per railed ship and derive rail_pos /
      rail_vel from absolute time. The elements are already computed for the
      orbit readout (render.cpp:170) and at park time (vehicle.cpp:2855), and
      propagateKepler already takes an absolute-time form for bodies, so the
      pieces exist. Would make rails exactly reproducible and delete this whole
      hazard class for ships, not just bodies. Do this before building any
      feature that needs a predictable future state (maneuver nodes, encounter
      prediction, multi-ship timewarp).

A3. [?] heading / pitch / roll are inertial-relative for a coasting ship.
                                                            COST: S (once decided)
    WHAT: Vs/Hs were just fixed (b5c2d20) to be surface-relative. Attitude was
      deliberately left alone: `facing` and `_up` are both in ship->frame, so
      they are self-consistent -- but for a ship on rails that frame is the
      INERTIAL node, so "heading" is relative to inertial north, not to the
      ground. It drifts from surface heading by the body's spin.
    WHERE: render.cpp:185-187 (_up/_north/_east from `pos`), :200-207
      (groundHed / heading / pitch / roll).
    DECISION NEEDED: what should the Surface window mean by Hdg? KSP shows
      surface-relative. Must be settled before building a landing HUD or an
      autopilot that flies a surface heading.

B. TRAPS AND DEAD CODE (all small, all safe, worth a single sweep)
=====================================================================

B1. [T] Frame::getRotFrame() returns children.front().              COST: S
    WHERE: frame.h:83-89. Correct ONLY because system.cpp:275 pushes each
      body's rotating frame into `children` before system.cpp:311 links the
      moons' inertial frames. Reorder those two passes and it silently returns
      a MOON's inertial frame instead of the spin frame -- with no crash, just
      wrong surface math.
    FIX: TerrainBody::rot_frame (terrain.h:147) is unambiguous and already
      there. The only reason it is not used is that frame.h forward-declares
      TerrainBody, so the inline body cannot dereference it -- move this one
      method into frame.cpp. Landmine in the most load-bearing struct in the
      sim; cheap to remove.

B2. [T] Frame::ang is dead state.                                   COST: S
    WHERE: declared frame.h:51, written frame.cpp:61, read NOWHERE in src/
      (verified by grep). It should be a local in UpdateOrbitRails. Keeping it
      as a member is what invited the `if(ang != 0)` bug removed in 4234fe6 --
      a stored field reads like state someone else depends on.

B3. [T] The build disables the unused-code warnings.                COST: M
    WHERE: Makefile:100 -- `-Wall -Wextra -Wpedantic` followed by
      `-Wno-unused-variable -Wno-unused-parameter -Wno-unused-but-set-variable`.
    WHY: this is why dead code survives unnoticed. Two confirmed examples:
      the `double &time = game.time;` alias in main.cpp (deleted in 4234fe6,
      dead at HEAD) and render.cpp:245-246, which binds ver_speed/hor_speed2 in
      draw3d and never reads them. More are likely.
    HOW: drop -Wno-unused-variable and -Wno-unused-but-set-variable first (the
      parameter one is noisier and more defensible for callback signatures),
      clear the fallout -- mostly deletions -- then leave them on. Cheap,
      permanent payoff: the compiler starts catching "computed a value nobody
      reads", which is exactly the class of bug that hides in a sim.

B4. [T] main.cpp's alias block invites the same mistake again.      COST: S
    WHERE: main.cpp:454-462 -- `Vehicle *&ship = game.ship;`,
      `int &time_accel = game.time_accel;`, etc.
    WHY: aliases make it hard to see what is Game state versus a local, and
      they can bypass the invariants that live on Game (e.g. writing `time`
      directly instead of going through setTime). Remove them incrementally as
      each region is touched; do not do it as a big-bang rename.

C. TEST INFRASTRUCTURE
=====================================================================

C1. [I] e2e timing is wall-clock and frame-dependent -> flaky.      COST: M
    WHAT: cases are driven by `--timeout <wall s>` and `--sim-press
      <ms,...>`, both measured from loop start (main.cpp:995, events.cpp:29),
      while the instrument logs print at most once per RENDERED frame
      (gameui.cpp:1469-1472 throttle). Under the runner's 2-job parallelism a
      slow case can render only a handful of frames, so assertions on sample
      counts break for reasons that have nothing to do with the code.
    OBSERVED: hit directly on 2026-09-25 -- the first version of
      title-load-spin passed alone and produced 0-1 samples in the battery.
      Worked around by lengthening the window and cutting the requirement to
      two samples, but that is a workaround, not a fix.
    HOW: a deterministic mode -- fixed dt, and timeouts/presses counted in
      FRAMES rather than wall-clock ms. Would make the suite faster (no
      real-time waiting), non-flaky under load, and would let assertions be
      exact instead of thresholded. High value: it is the difference between
      trusting a red test and re-running it three times.

C2. [I] The Surface/Orbit readout is formatted twice and can drift.  COST: S
    WHERE: gameui.cpp:1443-1462 (the ImGui SURFACE window) and
      gameui.cpp:1476-1505 (the --info-log printf), both from the same
      ShipView snapshot. They have ALREADY drifted: the printf carries `acc`
      and `alt_asl`, the window does not.
    WHY IT MATTERS NOW: e2e/run.py's `surf` series (added in 4234fe6) parses
      that printf with a strict regex (run.py SURF_RE). Change a field, a unit
      or the order and the series silently parses to nothing -- a case then
      fails on sample count rather than telling you the format moved.
    HOW: one shared formatter feeding both, or at minimum a comment on each
      pointing at the other and at SURF_RE.

C3. [I] .mimocode/ is untracked and not gitignored.                 COST: S
    WHERE: shows in every `git status`; .gitignore has no entry (tmp/ is
      covered, this is not). Add it, plus any other agent scratch dir, so it
      cannot be committed by accident.

C4. [I] Committed e2e fixtures are mutable and nothing checks them.  COST: S
    WHY: on 2026-09-25 a fixture (e2e/fixtures/save_railed/ships/v1.json) was
      silently overwritten mid-battery by a tool that was supposed to be
      read-only. Two cases failed with a confusing "two ships claim part uid 1"
      and the failure looked like flakiness. Caught only by hashing the fixture
      tree before and after the run.
    HOW: have e2e/run.py hash e2e/fixtures at start and verify at the end, and
      fail the battery loudly if anything moved. Consider also a structural
      sanity check of each fixture on load (distinct part uids across ships,
      every named ship file present) so a corrupt fixture reports itself
      instead of masquerading as a physics failure.

D. STRUCTURE (gradual, no behaviour change)
=====================================================================

D1. [S] main.cpp is 1355 lines with most of it inside main().       COST: M
    Pull the boot phases into named functions taking Game& -- renderer/shaders,
    mesh/texture load, fleet build, camera + focus setup, the one-shot hook
    block (--reload / --new-game / --switch-system at main.cpp:1055-1115).
    Easier to read, and it is where B4's aliases naturally die.

D2. [S] load_game is ~195 lines (save.cpp:630-824) with all five phases
    inline: read meta -> move clock -> detach old fleet -> build (with
    rollback) -> commit -> phase-2 cross-references.               COST: M
    It is careful and heavily commented, but the phases would be easier to
    trust as named functions -- especially now that the rollback is documented
    as PARTIAL (clock, frames, time_accel and exhaust_scale are not restored on
    a throw; see the comment at save.cpp:657-668). Extracting them would also
    make it obvious which state a refused load leaves behind.

D3. [S] TransferPlanner is a local in main.cpp, not a Game member.  COST: M
    WHERE: main.cpp:768 `TransferPlanner xferPlanner(game);` then threaded
      through the UI and draw calls.
    WHY: it holds sim-clock state (A1) that Game cannot reach, so the clock
    hook cannot invalidate it. Moving it into Game makes A1 a two-line fix and
    removes an awkward parameter from several signatures.

E. DESIGN DECISIONS (no code until decided)
=====================================================================

E1. [?] Should the title screen be allowed to warp the shared clock?
    WHAT: the title runs the real tick on the real clock (scene.cpp:133-142,
      `sim = true`) and the warp keys are scene-neutral (events.cpp:462-484),
      so a menu with no vessel can burn up to 100000x sim time. newGame
      (game.cpp:403-424) does NOT reset the clock, so a new game inherits
      whatever date the player left the menu at.
    STATUS: harmless now that setTime/syncRails exist -- this was the trigger
      for the snap bug, not its cause. Options if it ever feels wrong: clamp
      time_accel while the floor scene is Title with no vessel (the backdrop
      only needs 1x to turn), and/or setTime(0) in newGame so a new game always
      starts at epoch. Deferred deliberately on 2026-09-25.

E2. [?] Per-body rotation epoch (rot_angle0) and orbit epoch.       COST: S
    WHAT: today every body's spin is `fmod(rot_ang_speed * time, 2pi)`, so at
      t=0 every planet's prime meridian points the same way, and every orbit
      starts at its authored t=0 state (frame.cpp:61; orbit_pos0/orbit_vel0 in
      frame.h). initial_orient is identity for every body in every system
      (set only at system.cpp:196/250); axial tilt is carried by spin_axis.
    WHAT IT BUYS: planets that are not mysteriously aligned at epoch, and --
      the real reason -- authorable launch sites and ground tracks, i.e. "the
      pad is at THIS longitude when a new game starts". Becomes relevant when
      authoring real systems or surface facilities. Would also want a per-body
      orbit epoch so a system can start at an arbitrary date.
    NOTE: this is authoring flexibility, not correctness. It would NOT have
      prevented the snap bug. If added, the "orient is a pure function of time"
      invariant restated in frame.cpp becomes "of (time, epoch)".
